== Basisszenarien (müssen alle erfüllt werden)

=== Einfacher Change-Request

* Eingang des Change-Requests (Ticket-System, Template)
* Umsetzung im Branch (inkl. Referenz auf Ticket)
* Q-Gate (Code-Review, Tests, Quality-Checks)
* Merge-Request (inkl. erforderlicher Checks)
* Delivery und Deployment (Pfad bis in Zielumgebung beschreiben)


== 1. Einfacher Change-Request

Ein Change-Request beginnt typischerweise mit der Erstellung eines neuen Branches.
Die Pipeline unterscheidet dabei folgende Typen:

* *feature/* – neue Funktionalität
* *bugfix/* – Fehlerbehebung
* *hotfix/* – dringende Korrektur
* *main* – stabiler Hauptbranch

Sobald auf einem dieser Branches ein Commit gepusht wird, startet die Pipeline automatisch (ausser bei Tags).
Der main branch ist wie üblich geschützt.


== 2. Umsetzung (Build & Vorbereitung)

Die technische Umsetzung eines Changes beginnt in der Pipeline mit der *build*-Stage.
Hier werden Backend und Frontend automatisch gebaut:

=== Backend Build

* Wird für jeden Branch ausgeführt.
* Baut das Artefakt mittels Maven und Jib.
* Erzeugt ein Docker-Image, getaggt mit dem Commit-SHA.
* Push zum Container Registry.

=== Frontend Build

* Analog zum Backend-Build.
* Docker-Image wird gebaut und ins Registry gepusht.

Diese Build-Prozesse bilden die Grundlage für spätere Test- und Deployments, da die Images auf Test- und Produktionssystemen wiederverwendet werden.

== 3. Q-Gate

Das Q-Gate definiert, ob ein Change sauber gebaut und grundlegend geprüft wurde.
Aus Sicht dieser Pipeline besteht das Q-Gate aus:

* erfolgreichem Build inkl. der Unit- und Integrationstests von Backend und Frontend
* erfolgreicher SAST Analyse

Je nach Branchtyp ist auch relevant, ob ein Deployment manuell bestätigt werden muss (z.B. für Feature, Bugfix, Hotfix).
Damit ist das Q-Gate ein technischer Qualitätsfilter, bevor ein Merge-Request erstellt und bewertet wird.

== 4. Merge-Request (Code Review & Freigabe)

Nachdem ein Change erfolgreich gebaut und durch das Q-Gate gegangen ist, kann ein Merge-Request erstellt werden.

Der Merge-Request profitiert von:

* automatisch erzeugten Build-Artefakten (Docker-Images)
* SAST-Bericht

Für den Merge in den *main* Branch ist wesentlich, dass:

* der Change sauber gebaut wurde
* alle Testergebnisse erfolgreich sind
* Reviews und Freigaben abgeschlossen sind (4 Augenprinzip)

Sobald der Merge erfolgt, startet eine neue Pipeline auf *main*, die als Grundlage für die Delivery dient.

== 5. Delivery (Bereitstellung auf Testumgebung)

Jeder Change, der in einem Feature-, Bugfix- oder Hotfix-Branch stattfindet, kann manuell auf der Testumgebung deployed werden.
Alternativ kann der Hotfix branch auch manuell auf Prod deployen werden
Führt man den Merge in den *main* Branch durch, wird das Test-Deployment *automatisch* angestossen.

Das Deployment auf Test:

* erzeugt eine `.env.test` Datei mit Test-Passwörtern und DB-Informationen
* lädt die passenden Docker-Images (beide Services nutzen das Commit-SHA)
* startet die Anwendung via `docker compose`
* lässt das System mittels `--wait` hochfahren

Dies bildet den Schritt der Delivery, also die Bereitstellung für Qualitäts- und Abnahmetests.

== 6. Deploy (Prod-Rollout)

Das Deployment auf die Produktionsumgebung erfolgt kontrolliert und ist grundsätzlich *manuell*, selbst für *main*.

Der Ablauf ist analog zum Test-Deployment:

* Erstellung der `.env.prod` Datei
* Stop und Neustart der Compose-Services
* Laden der neuen Images
* Start mit Health-Wait

Die Entscheidung, wann ein Change produktiv geht, wird bewusst manuell getroffen – typischerweise nach erfolgreicher Abnahme auf der Testumgebung.

== Zusammenfassung des Lebenszyklus

[cols="1,3",options="header"]
|===
|Phase |Beschreibung

|Einfacher Change-Request
|Branch wird erstellt, Pipeline startet automatisch.

|Umsetzung
|Build von Backend und Frontend, SAST Sicherheitsprüfung.

|Q-Gate
|Build und Tests müssen erfolgreich sein, Branch-Regeln müssen passen.

|Merge-Request
|Review, Diskussion und Freigabe. Nach Merge in main startet eine neue Pipeline.

|Delivery
|Automatisches (main) oder manuelles (feature/bugfix/hotfix) Deployment auf Test.

|Deploy
|Manuelles Deployment auf Produktion; stabiler, kontrollierter Rollout.
|===

=== Neuer Mitarbeitender: Aufsetzen der Entwicklungsumgebung

Dieses Kapitel beschreibt, wie ein neuer Mitarbeitender die komplette Entwicklungsumgebung selbstständig einrichten kann. Ziel ist, dass nach dieser Anleitung ein erster Build läuft und ein einfacher End-to-End-Workflow (Code ändern, testen, pushen) für Backend (Java Micronaut, Java 21) und Frontend (Svelte) funktioniert.

==== Voraussetzungen

* Studenten-Account an der HSLU ist aktiv und E-Mail-Adresse ist bekannt
* SWITCH GitLab-Account ist erstellt und mit dem Studenten-Account verknüpft
* Zugriff auf folgende GitLab-Projekte ist vorhanden:
** https://gitlab.switch.ch/hslu/edu/bachelor-computer-science/devops/25hs01/g01/g01-form[GitLab Projekt Applikation]
** https://gitlab.switch.ch/hslu/edu/bachelor-computer-science/devops/25hs01/g01/g01-monitoring[GitLab Monitoring Projekt]
** https://gitlab.switch.ch/hslu/edu/bachelor-computer-science/devops/25hs01/g01/g01-documentation[Projekt Dokumentation]
* Hardware:
** Laptop mit aktuellem Betriebssystem (Linux oder macOS bevorzugt, Windows mit WSL2 möglich)
** Adminrechte für lokale Installationen

==== SSH-Key erstellen und SSH-Zugriff prüfen

. Studenten-Account aktivieren und Passwort setzen (falls noch nicht erfolgt).
. SSH-Zugriff auf die GitLab-Plattform testen:
+
[source,bash]
----
git clone git@gitlab.switch.ch:hslu/edu/bachelor-computer-science/devops/25hs01/g01/g01-form.git
----

. Falls der Zugriff scheitert:
.. SSH-Key generieren (Falls nicht schon vorhanden):
+
[source,bash]
----
ssh-keygen -t ed25519 -C "vorname.nachname@stud.hslu.ch"
----

.. Den Public Key (`~/.ssh/id_ed25519.pub`) im GitLab-Profil unter *SSH Keys* hinterlegen.
. SSH-Zugriff erneut testen (z.B. mit `git clone` oder `ssh -T git@gitlab.switch.ch`).

==== Installation der Basis-Tools

Folgende Tools müssen lokal installiert sein:

* Git (Kommandozeile)
* Container-Engine Docker
* Java Development Kit (JDK) 21
* Maven
* Node.js (LTS) und npm für das Svelte-Frontend
* Editor/IDE (z.B. VS Code, IntelliJ IDEA)

Schritte:

.. Folge der offiziellen Installationsanleitung unter
https://git-scm.com/install/[https://git-scm.com/install/]

+

.. Folge der offiziellen Installationsanleitung unter https://docs.docker.com/engine/install[https://docs.docker.com/engine/install], um Docker zu installieren.

docker run --rm hello-world

.. Folge der offiziellen Installationsanleitung unter https://adoptium.net/temurin/releases/?version=21[https://adoptium.net/temurin/releases/?version=21], um JDK 21 zu installieren.
.. Prüfe die installierte java version:
+
[source,bash]

.. Folge der offiziellen Installationsanleitung unter https://maven.apache.org/install.html[https://maven.apache.org/install.html], um Maven zu installieren.
.. Prüfe die installierte Maven version:
+
[source,bash]

----

.. Folge der offiziellen Installationsanleitung unter https://nodejs.org/en/download/package-manager/[https://nodejs.org/en/download/package-manager/], um Node.js und npm zu installieren.
.. Prüfe die installierten Versionen:
+
[source,bash]

. IDE installieren und grundlegende Plugins / Extensions einrichten:
.. Installiere z.B. Visual Studio Code von https://code.visualstudio.com/[https://code.visualstudio.com/] oder IntelliJ IDEA von https://www.jetbrains.com/idea/download/[https://www.jetbrains.com/idea/download/].
.. Füge folgende Extensions/Plugins hinzu falls nicht schon vorhanden:

==== Projekt auschecken und lokal starten

. Haupt-Repository clonen:
+
[source,bash]
----
git clone git@gitlab.switch.ch:hslu/edu/bachelor-computer-science/devops/25hs01/g01/g01-form.git
cd g01-form
----

. Postgres-Datenbank via Docker-Compose starten:
+
[source,bash]
----
docker compose -f docker_local.yml up -d
----

. Backend-Abhängigkeiten installieren und Backend bauen und ausführen:
+
[source,bash]
----
cd backend
mvn package
MICRONAUT_ENVIRONMENTS=local java -jar ./target/g01-form-0.1.jar
----

. Frontend-Abhängigkeiten installieren und Frontend bauen und ausführen:
+
[source,bash]
----
cd ../frontend
npm install
npm run dev
----

Backend ist nun auf http://localhost:8080 und Frontend auf http://localhost:3000 erreichbar.

==== Arbeiten mit der Branching-Strategie

Kurzüberblick (Details im eigenen Kapitel *Branching-Strategie*):

. Neues Ticket im Issue-Tracker auswählen oder zugewiesen bekommen.
. Lokalen Branch gemäss Konvention erstellen:
+
[source,bash]
----
git checkout -b feature/<kurze-beschreibung>
----

. Änderungen implementieren, Tests lokal ausführen:
+
[source,bash]
----
# Backend-Tests
cd backend
mvn test

# Frontend-Tests
cd ../frontend
npm test
----

. Commiten mit aussagekräftiger Nachricht:
+
[source,bash]
----
git commit -am "feat: <kurze beschreibung>"
----
. Branch pushen und Merge-Request öffnen.

==== CI/CD-Integration prüfen

. Nach dem ersten Push sicherstellen, dass die CI-Pipeline auf GitLab automatisch startet.
. Pipeline-Status beobachten (grün/rot).
. Bei Fehlschlägen Logs in der CI/CD-Oberfläche ansehen und Probleme beheben.
. Sicherstellen, dass:
** Unit-Tests für Backend (Maven) laufen
** Unit-/Component-Tests für Frontend (Svelte) laufen
** Linting / Static Code Analysis läuft
** Artefakte/Container-Images gebaut und in die Registry gepusht werden

==== Typische Probleme und Lösungen

* **Git-Zugriff verweigert**
** SSH-Key fehlt oder ist nicht im GitLab-Profil hinterlegt
** HTTP(S)-Credential falsch - im Git-Client aktualisieren
* **Backend-Build läuft lokal nicht durch**
** Prüfen, ob JDK 21 installiert und aktiv ist
** Prüfen, ob alle Abhängigkeiten heruntergeladen wurden (`mvn dependency:resolve`)
* **Frontend-Build läuft nicht durch**
** Prüfen, ob Node.js LTS verwendet wird
** `node_modules` gegebenenfalls löschen und `npm install` erneut ausführen
* **Container kann nicht gestartet werden**
** Prüfen, ob Docker-Dienst läuft
** Port-Konflikte: andere Dienste beenden oder Port im Config-File / `docker-compose` anpassen

==== Checkliste für erfolgreiches Onboarding

Ein neuer Mitarbeitender gilt als vollständig aufgesetzt, wenn:

* [ ] Git-Zugriff funktioniert (clone, pull, push)
* [ ] Backend-Build (Micronaut, Java 21) lokal erfolgreich durchläuft
* [ ] Frontend (Svelte) lokal gebaut und gestartet werden kann
* [ ] CI-Pipeline für einen eigenen Branch erfolgreich läuft
* [ ] Mindestens ein kleiner Change-Request (z.B. Dokumentation oder kleine UI-Änderung) komplett durch den Prozess  
  (Issue → Branch → MR → Review → Merge → Deployment in eine Nicht-Prod-Umgebung) gelaufen ist

=== Fazit & Massnahmen (für Abgabe entfernen)

Du hast völlig recht, Skepsis war angebracht. Wir haben zwei "Baustellen":

1.  **Faktor 12 (Admin-Prozesse):** Dies ist der kritischste Punkt.
* *Lösung:* Migrationstool (Flyway) einführen und Migrationen als separaten CI-Job oder Init-Container ausführen.

2.  **Faktor 10 (Dev-Prod-Parität):** Hier gibt es Abweichungen im Workflow.
* *Lösung:* Die `README.md` sollte primär die Entwicklung _innerhalb_ von Docker (z.B. via `docker compose -f docker_test.yml up`) propagieren, statt der lokalen Java/Node-Befehle, oder DevContainer nutzen, damit die lokale Umgebung der Produktion gleicht.
