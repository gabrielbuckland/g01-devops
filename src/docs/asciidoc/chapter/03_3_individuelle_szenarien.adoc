== Individuelle Szenarien

Im Rahmen dieses Projekts haben wir uns entschieden, die Datenbank-Migrationen vollständig zu automatisieren. Ziel ist es, manuelle Eingriffe auf den Produktivsystemen zu eliminieren und gleichzeitig die Reproduzierbarkeit aller Umgebungen (Local, Test, Prod) sicherzustellen.

=== Migration der Persistenz (Schema) mit Flyway

Dieses Szenario beschreibt die Integration und Nutzung von Flyway für das versionierte Management von Datenbankschemata.

==== Kontext und Begründung

In einer modernen DevOps-Umgebung muss die Datenbank-Infrastruktur genauso flexibel und versionierbar sein wie der Applikationscode („Infrastructure as Code“). Manuelle SQL-Updates sind fehleranfällig, schwer nachvollziehbar und lassen sich zwischen Umgebungen kaum reproduzieren.

Für das Projekt `g01-form` ist der Einsatz von Flyway besonders relevant, da eine strikte Trennung von Code und State im Sinne der 12-Factor-App angestrebt wird. Zudem muss die Datenbank beim Deployment neuer Backend-Versionen automatisch auf den aktuellen Stand gebracht werden. Nur so kann sichergestellt werden, dass lokale Entwicklungsumgebungen exakt dasselbe Schema verwenden wie die Test- und Produktionsumgebungen.

==== Ablauf und Prozessbeschreibung

Eine Schema-Änderung erfolgt in einem klar definierten, durchgängigen Prozess. Zunächst erstellt ein Entwickler ein neues SQL-Migrationsskript im Ordner `src/main/resources/db/migration`. Die Benennung folgt der Konvention `V<Version>__<Beschreibung>.sql`, beispielsweise `V1__create_form_table.sql`.

Beim lokalen Start des Backends über Docker Compose (`docker_local.yml`) wird dieses Skript automatisch durch Flyway gegen die lokale PostgreSQL-Datenbank ausgeführt. Anschliessend wird das Skript gemeinsam mit dem restlichen Backend-Code ins Git-Repository gepusht und im CI-Prozess als Teil des Backend-Artefakts (JAR bzw. Docker-Image) gebaut.

Beim Deployment auf die Test- oder Produktionsumgebung prüft Flyway beim Start des neuen Backend-Containers die Tabelle `flyway_schema_history`. Erkennt Flyway ein Migrationsskript im Classpath, das in der Datenbank noch nicht angewendet wurde, wird dieses automatisch ausgeführt. Erst wenn alle Migrationen erfolgreich abgeschlossen sind, startet die Applikation vollständig und der Healthcheck wird grün.

==== Beteiligte Systeme und Rollen

Die Versionierung und Ausführung der Migrationen erfolgt durch Flyway als Library. Die Einbindung geschieht beim Applikationsstart über Micronaut (`micronaut-flyway`). Als Zielsystem dient PostgreSQL, welches sowohl die eigentlichen Tabellen als auch die Migrationshistorie in der Tabelle `flyway_schema_history` speichert. Die Verantwortung für korrekte, inkrementelle SQL-Migrationen liegt bei den Entwicklern.

==== Dokumentation der Ergebnisse

Die Integration von Flyway wurde erfolgreich umgesetzt. Änderungen am Datenbankschema sind nun vollständig versioniert und direkt im Code nachvollziehbar.

Abhängigkeiten (`pom.xml`):
[source,xml]
----
<dependency>
    <groupId>io.micronaut.flyway</groupId>
    <artifactId>micronaut-flyway</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
----

Konfiguration (`application.properties`):
[source,properties]
----
datasources.default.schema-generate=NONE
flyway.datasources.default.enabled=true
flyway.datasources.default.locations=classpath:db/migration
----
Die automatische Schema-Generierung durch Hibernate bzw. JPA ist bewusst deaktiviert, damit Flyway die vollständige Kontrolle über das Datenbankschema behält.

Beispiel einer Migration (`V1__create_form_table.sql`):
[source,sql]
----
CREATE TABLE form (
    id UUID PRIMARY KEY,
    firstname VARCHAR(255) NOT NULL,
    lastname VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
----
